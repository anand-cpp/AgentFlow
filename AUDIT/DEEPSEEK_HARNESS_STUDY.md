## 1. Status warning — read this first

The project's own `SAFETY.md` says, verbatim:

> "DeepSeek Harness is experimental developer-preview software. It has not undergone a security
> audit and must not be treated as secure or production-ready."

> "Sandboxing, approval prompts, and permission controls can reduce risk, but they do not guarantee
> isolation or prevent damage."

> "Do not rely on DeepSeek Harness as the sole security control for untrusted workloads."

This is a vendor stating its own agent framework is unaudited. That does not make it a poor
architectural reference — it makes it a **risky dependency**. AgentFlow must not inherit that
posture; it must do better. Recorded here because shipping an unaudited agent framework and
calling it a professional product would be dishonest.

## 2. Scale and structure

`pnpm` workspace, `pnpm@11.7.0`, Node `^22.19.0 || >=24.0.0`. 57 packages, 4 apps
(`cli`, `desktop`, `desktop-host`, `web`), plus `python/`, `native/`, `vendor/`, `benchmarks/`,
`snapshots/`, `website/`.

Deeply i18n'd — every doc has `.md`, `.zh.md`, and `.i18n.yaml`. `BRAND_GUIDELINES.md`,
`CONTRIBUTING.i18n.yaml`, `README.i18n.yaml`, `SAFETY.i18n.yaml`.

### The framework: Cordis

Vendored into `vendor/` under `@deepseek-ai/*` (each preserving upstream `LICENSE`):
`cordis`, `cosmokit`, `schemastery`, `logger-console`, `timer`, `loader`, `hmr`, `group`,
`include` — all MIT.

The core idea, from `docs/architecture.md`:

> "Every part of the product is a plugin, including the model adapter, the tool registry, the
> session log, and the agent loop itself, so each is replaceable from configuration. There is no
> privileged core to patch."

Plugins contribute **services**, **typed events**, and **reversible effects** to a shared context
(`ctx`). Registrations are effects that unwind on unload.

## 3. The three ideas worth taking

### 3.1 Profiles and bundles — composable, patchable application assembly

| Concept | Definition |
|---|---|
| **Bundle** | A distribution format for Cordis config rows + the code they mount. Declares itself via a `dsh` field in its own `package.json` (`dsh.bundle` → patch file). |
| **Profile** | A named composition stored in Harness home. Lists ordered bundles, holds out-of-tree plugins and the user's `cordis.patch.yml`. Declares via `dsh.profile`. |

Shipped profiles: `web`, `headless`, `sdk`, `sdk-minimal`, `acp`.

Layer application order onto an empty entry list:

```
profile's bundles (in listed order)
  -> profile's cordis.patch.yml
  -> home-level cordis.patch.yml
  -> --patch overlay
```

A patch targets a row by id and replaces its whole config or inserts new rows. And you can just
look at what your machine boots:

```sh
dsh --profile web --dump-config
```

**Why this matters for AgentFlow:** the directive requires a config hierarchy with documented
precedence *and* a plugin system. DeepSeek's answer is "an ordered layer list where every layer is
inspectable and individually overridable." That is strictly better than a precedence table in a
README, and it is implementable without a plugin framework — an ordered array of config layers
merged in sequence, with a command that prints the resolved result.

Also note `dsh-headless` — "a one-shot runner with no server." That is exactly the AgentFlow CLI
shape: no HTTP server, no dashboard.

### 3.2 The tool execution pipeline — the single most valuable artifact found

`docs/tool-execution-pipeline.md` (generated by `scripts/gen-doc-graphs.ts`) documents a
**three-waterfall pipeline** that runs around every tool call *without changing the agent loop*:

```
1. tools/pre-execute   waterfall   hooks, permission, sandbox   -> allow | deny | ask
2. registered monotonic guards       deny or abstain; identity protected
3. tools/execute       waterfall   timeout, retry, metrics (around dispatch)
   -> tool body execute()
   -> fs/write-intent | fs/edit-intent   (tool-fs mutations only)
4. tools/post-execute  waterfall   accept, block, replace, add context
5. registry outer normalization     pipeline/result snapshot throws become isError
6. ToolDefinition.finalizeContent   last content-only invariant
7. tools/result        synchronous  frozen authoritative outcome
```

Critical design properties:

- **The tool call is logged as a session event *before* execution** (`tool/call`). A crash mid-tool
  leaves a record that it was attempted.
- **Monotonic guards**: deny or abstain, and *identity is protected* — a guard cannot be talked out
  of denying.
- **Approval is one-shot** (`ctx.approval`), and **absent or unanswerable ⇒ deny**. Fail-closed.
- **Approval happens after pre-execute, before guards**, so an approved call is still checked.
- **Steps 1–6 may each transform the call**; the three waterfalls are not just gates.
- **Any throw anywhere is normalized** into an `isError` result rather than crashing the loop.
- **`tools/result` is synchronous and frozen** — "the single model-facing outcome," one per tool
  call. Exactly one outcome, not several partial ones.
- **Additional contexts go in after the recorded result**, FIFO, injected as user/message — so
  tool-observed content is injected *after* the transcript record, in order.
- UI is presentational: `presentCall(args)` before, `presentResult(args, result)` after. The UI
  never participates in the decision.

This is the reference design for AgentFlow's tool registry and permission system. Note it is
*more* explicit than OpenCode's `evaluate()`-and-`ask()`, and the two compose: DeepSeek's waterfall
is the skeleton, OpenCode's wildcard ruleset is the policy that `pre-execute` consults.

### 3.3 `docs/defensive-patterns.md` — bug classes that actually shipped

The most practically valuable document in either reference repo. Framing: *"each pattern below is
a class of defect that actually shipped or nearly shipped here, stated as the rule that prevents
its recurrence."*

| Pattern | Rule |
|---|---|
| **Orthogonal outcomes** | A process can time out **and** exit 0 because it trapped the signal. Surface `timedOut`, `signal`, `exitCode` independently. Never nest one flag inside another's branch, or a cut-short run reads as clean success |
| **Honor contracts on BOTH sides** | Normalize all representations of one outcome before returning. `LlmAdapter.stream()` may throw or emit `finish {error\|aborted}`; `LlmRuntime.stream()` exposes only terminal finish chunks. Middleware defects stay thrown |
| **Async state ≠ sync state** | `agent.followup()` has no per-message completion. Several queued follow-ups, steering, and injected work may share one `running` interval. Define an explicit interval, and handle "the awaited transition can never occur" or the wait hangs |
| **Dispose must reach quiescence** | `kill` **then `await done`**. Close listener/notification registries **before** killing, so late completions stay silent |
| **Contain callback exceptions** | Wrap the dispatch loop in try/catch and log. One bad subscriber never breaks core lifecycle |
| **Never hand untrusted output the ambient environment** | Scrub spawned-command env: drop `*KEY*`/`*SECRET*`/`*TOKEN*`/`*PASSWORD*` so harness credentials can't leak into output, `env`, or spill files |
| **Private temp/spill paths** | Private `0700` dir, random names, exclusive owner-only opens (`'wx'`, `0o600`) — predictable world-readable paths invite symlink races |
| **Unlink link-shaped paths** | `lstatSync().isSymbolicLink()` then `unlinkSync` — deletes only the link, refuses a real directory. Windows `rmSync(junction)` throws `ERR_FS_EISDIR`; recursive delete may descend into the target. Reserve recursive `rmSync` for known real directories |

**The env-scrubbing rule and the junction rule are directly load-bearing for AgentFlow** — the first
serves the directive's secret-redaction requirement, the second is a live Windows hazard given the
project targets Windows users (this very audit runs on Windows).

Every extension runner has its own `guard.ts`, `sandbox.ts`, and `inspect-registry.ts`. **Capability
gating is per-package, not global.** Lesson: build the guard into the extension point itself.

## 4. Documentation and compliance engineering worth copying

Upstream 9Router has **no** `SECURITY.md` and **no** `CONTRIBUTING.md`. DeepSeek has both, plus:

- **`THIRD_PARTY_NOTICES.md` — generated, not hand-written.**
  `scripts/gen-third-party-notices.ts`, a **pre-commit hook regenerates it** whenever a staged file
  changes an input, and `scripts/gen-third-party-notices.spec.ts` **asserts in the test lane that
  the committed bytes match**. `pnpm run verify-third-party-notices` for a standalone check.
  It documents the failure mode explicitly: *"Deleting a manifest runs no hook, so that case is
  caught by the assertion instead."*

  **This is the answer to `DEPENDENCY_AUDIT.md` §3.** Generate notices; verify by test, not by
  discipline.

- **`vendor/README.md`** records exact upstream commits and local modifications per vendored package.
  Precisely the provenance discipline the directive demands.

- **Generated diagrams with verification.** `gen-doc-graphs.ts` emits the pipeline and module-graph
  docs. A committed `docs/dependency-catalog.json`, `docs/persistence-catalog.md`,
  `docs/persistence-schema.json`, `docs/config-catalog.md`, `docs/tool-catalog.md`,
  `docs/module-graph.md`, `docs/graph-atlas.md`.

- **`docs/testing.md`** pairs with defensive patterns: "test-tier counterparts (real entry path,
  world-verification, resource ownership)."

- Multiple test lanes as separate configs: `vitest.config`, `.e2e`, `.web`, `.web-stress`, `.web.perf`,
  `.bench`, `.snapshot`, `.expected`. Plus `lefthook.yml`, `Makefile`, `.jscpd.json` (copy-paste
  detection), `.oxlintrc.json` + `.oxlintrc.staged.json`, `pytest.ini`.

- **`scripts/verify-application-entrypoints.ts`** classifies every bin/executable/script and
  *rejects* an application path that bypasses the sanctioned launcher. Enforcement as a test.

## 5. What to take — and what must not be taken

### Adopt as design inspiration

| Idea | Why |
|---|---|
| **Three-waterfall tool pipeline** (pre-execute / execute / post-execute) + monotonic guards + one-shot fail-closed approval + normalized errors + single frozen `tools/result` | The best-documented tool-safety design found in any reference |
| **Ordered config layers, individually overridable, inspectable via a dump command** | Turns a precedence table into a verifiable mechanism |
| **`defensive-patterns.md` as a required reading, seeded from real defects** | Cheap, high-yield correctness discipline |
| **Generated `THIRD_PARTY_NOTICES.md` + pre-commit regen + test-lane byte assertion** | Automates the exact gap found in `DEPENDENCY_AUDIT.md` §3 |
| **`vendor/README.md`-style per-component commit + modification log** | Provenance as a maintained artifact |
| **Env scrubbing on every spawned command** (`*KEY*`/`*SECRET*`/`*TOKEN*`/`*PASSWORD*`) | Directly satisfies the secret-redaction requirement |
| **Private `0700` + random names + `0o600` exclusive opens for temp/spill** | Blocks symlink races |
| **Symlink-safe unlink; never recursive-delete an unverified path** | Live Windows hazard |
| **Dispose-to-quiescence: `kill` then `await done`; close registries before killing** | Prevents orphans |
| **Report orthogonal outcomes independently** | Prevents "timed out but exit 0" reading as success |
| **Per-extension `guard.ts` / `sandbox.ts` / `inspect-registry.ts`** | Capability gating at the extension point |
| **Entry-point verification as a test** | Prevents architectural drift |
| **A `headless` profile with no server** | Confirms the terminal-only shape |

### Do NOT take

- **No source copying.** MIT permits it; coherence does not. This is a pnpm/TypeScript/Cordis
  architecture with vendored framework internals.
- **Do not adopt Cordis.** A DI container with reversible effects is a rewrite, not a dependency.
- **Do not adopt the alpha posture.** `0.2.1-alpha.1`, self-declared unaudited. Take the design
  discipline; do not inherit the risk statement.
- **Do not copy the i18n apparatus.** ~3× doc duplication across 20+ languages is a large
  maintenance surface for a project at the pre-release stage. Do it later if ever.
- **Ignore `benchmarks/`, `snapshots/`, `website/`, `python/`, `native/`.** Out of scope.
- **Do not assume `computer-use` / `browser-use` belong in v1.** They are the highest-risk
  capabilities and the directive does not require them.

## 6. Cross-reference: three implementations of one idea

| Problem | 9Router | OpenCode | DeepSeek Harness |
|---|---|---|---|
| Context/tool-output overflow | `open-sse/rtk/` — `tool_result` token compression, fail-open | `tool/truncate.ts` + `truncation-dir.ts` — truncate + spill to disk | `spill/`, `spill-local/`, `spill-policy/` — retention, cleanup, multimodal recovery |
| Permission evaluation | none | `permission/index.ts` — `(permission, pattern)` wildcard ruleset, `findLast`, default `ask`, `Deferred` + finalizer | `interaction/` + `tools/pre-execute` waterfall; one-shot, absent ⇒ deny; monotonic guards |
| Tool registry | none | `tool/registry.ts` — builtin + plugin, filtered per agent/model | `core/tools` — scoped registry + guarded execution pipeline |
| Extension/plugin model | `skills/` (content only) | `plugin/` — typed `ToolDefinition`/`ToolContext` | Cordis — every component is a plugin |

**Conclusion:** AgentFlow's tool pipeline should merge OpenCode's ruleset evaluation into
DeepSeek's waterfall skeleton. That composition is not present in either reference and is genuine
new design work.

---

## 7. Net assessment

DeepSeek Harness contributes three things OpenCode does not: a **documented tool-execution
pipeline**, **ordered composable config layers**, and a **defensive-patterns discipline grounded in
shipped defects**. Those three are worth more than the rest of the repository combined, and all
three are directly implementable in plain JavaScript.

Its warnings are equally valuable and must be carried forward as requirements: unaudited, no
guaranteed isolation, approval prompts are not a security boundary. AgentFlow should state its own
threat model in `SECURITY.md` rather than shipping an agent framework that disclaims one.

This closes open item 2 in `LICENSE_AUDIT.md` §6: DeepSeek Harness's license is verified MIT at
file level, with vendored MIT components (`vendor/README.md` records each upstream commit and local
modification). Code-level engagement would be legally permitted — and is still declined on
engineering grounds.
